# M1 知识网络框架与编号体系

> 这份文档是整个库的**骨架**。所有后续内容都挂在它的某个节点上，所有检索都从它的编号出发。
> 维护原则：节点可以增补，编号不复用；一个知识点只归一个主节点，但可以被多个节点交叉引用。

## 1. 为什么是"网络"而不是"目录树"

纯目录树的问题是：一个知识点只能挂在一处，检索时容易漏。工程实际里，"路口冲突预警"这件事同时属于
运行管控（安全应用）、车路协同（协同感知）、人工智能（目标检测与轨迹预测）、支撑技术（感知与通信）。
所以框架采用**树形骨架 + 网状关联**：

```text
        树形：负责"找得到"                网状：负责"想得全"
   ┌──────────────────────┐        ┌──────────────────────────┐
   │ 域 → 主题群 → 专题   │   +    │ 跨域关联表 / 标签 / 场景链 │
   └──────────────────────┘        └──────────────────────────┘
              编号唯一                      一个场景串起 4–6 个节点
```

## 2. 六域总览

| 代码 | 域 | 回答什么问题 | 我的角色定位 |
| --- | --- | --- | --- |
| **M** | 元知识 | 这个领域怎么理解、怎么查、怎么讲 | 全局视角 |
| **T** | 智能交通运行管控 | 路网跑得怎么样、怎么让它更安全更顺畅 | **主专业** |
| **V** | 车路协同 | 车与路怎么协同、系统怎么建怎么运营 | 主战场 |
| **A** | 人工智能 | 用什么模型把数据变成判断与决策 | 能力放大器 |
| **S** | 支撑技术 | 被多域复用的底层技术（感知/定位/平台/安全） | 工具箱 |
| **I** | 产业与治理 | 标准、政策、钱、人 | 落地约束 |

!!! tip "主次关系"
    **T 是目的，V 是手段，A 是工具，S 是基础，I 是边界。**
    任何一个项目问题，先落到 T（要解决什么交通问题），再找 V/A/S 的组合，最后用 I 校验合规与可交付性。

## 4. 跨域关联：几个典型"场景链"

这是把树变成网的关键——**每个真实问题都是一条跨域链路**：

### 链路 1：高速公路团雾预警与限速

```text
T2.4 气象感知（能见度检测）
   └─▶ T3.1 风险评估（能见度-车速-制动距离模型）
          └─▶ T3.2 速度管控（分级限速策略）＋ T3.5 预警发布（VMS/广播/V2X）
                 └─▶ V2.2 通信（RSI 事件下发）＋ V4.2 预警应用（车端提醒）
                        └─▶ I1 标准（团雾预警阈值是否有国标依据）＋ S6 合规
```

### 链路 2：城市路口冲突预警

```text
A1.3 多目标跟踪 ＋ A2.4 行人识别
   └─▶ V3.2 雷视融合（路侧感知）
          └─▶ T3.1 冲突分析（TTC/PET 判定）
                 └─▶ V2.3 RSM 消息 ──▶ V4.2 车端预警
                        └─▶ T3.6 效果评价（冲突率下降多少）
```

### 链路 3：重点营运车辆（两客一危）动态管控

```text
T2.2 轨迹与重识别 ＋ T3.3 重点车辆管控
   └─▶ V1.2 云控平台（车辆画像与轨迹回放）
          └─▶ A3.1 轨迹预测（风险行为预判）
                 └─▶ T3.5 分级预警（车端/企业/监管三端）
                        └─▶ T5 应急处置（事件闭环）
```

### 链路 4：干线绿波 + 车路协同车速引导

```text
T4.2 干线协调（配时方案）
   └─▶ V2.3 SPAT 消息（相位与时序）
          └─▶ V4.3 GLOSA 车速引导
                 └─▶ S3.2 纵向规划（按信号优化到站时间）
                        └─▶ T1.3 评价（延误/停车次数/油耗）
```

## 5. 使用约定

### 5.1 编号怎么用

| 用途 | 写法 | 示例 |
| --- | --- | --- |
| 文档命名 | `NN.中文标题.md`，NN 与 L1/L2 顺序对应 | `03.主动安全管控.md` |
| 文内引用 | 直接用编号 | "见 T3.2 速度管控" |
| 标签 | `#T3.2`，用于全文检索与后续打标 | `tags: [T3.2, V4.2]` |

### 5.2 新增内容的判断顺序

1. 它解决什么**交通问题**？→ 先归到 T 域
2. 靠什么**系统/协同**实现？→ V 域
3. 用了什么**模型/算法**？→ A 域
4. 依赖什么**底层技术**？→ S 域
5. 受什么**标准/政策/商业**约束？→ I 域
6. 拆不准就放 M4.3（工作方法）暂存，日后归位。

### 5.3 不做的事

- 不追求"每个节点都写满"，**空白也是信息**（✗ 标记告诉你该补什么）。
- **不搬移、不索引原始素材**：素材是原料，知识库是产品，只沉淀提炼后的结论。
- 不为凑字数写"综述式空话"，宁可留一行"待补"。
